# 代码维护原则

## 1. 架构与目录组织
- 保持架构清晰，修改集中在所属模块，避免同一功能分散补丁。
- 不使用软链接组织代码，不增加仅用于调用另一个文件的空壳文件。
- 功能代码放在对应源码目录，脚本目录只放启动和运维脚本，不把功能代码放入日志或脚本目录。

## 2. Git 与临时产物
- 仓库只保留正式源码、必要配置、启动脚本、文档和长期维护的测试。
- 临时验证代码、一次性实验、日志、dump、缓存、备份和中间产物，从创建时就放在项目根目录的 `cache/` 下，与源码仓库分离，不纳入 Git。不要散放在源码目录后再靠大量忽略规则隐藏。
- `.gitignore` 只保留少量、明确、必要的兜底规则，避免宽泛规则误隐藏正常源码和配置。

## 3. 及时归档
- 工作根目录按项目组织，一个项目一个文件夹；不要在工作根目录平铺实验、备份或归档目录。
- 本项目统一使用 `/mnt/share/l00804615/glm5.3_flash_native/cache/` 存放临时内容；当前任务放 `cache/work/`，结束后整理到 `cache/archive/时间戳_用途/`，不另建并列的 `glm53-work`、`glm53-*-backups` 等目录。
- 归档名称保留时间和用途，便于追溯；需要长期维护的成果再有选择地纳入仓库。

## 4. 启动脚本简洁
- 根目录激活脚本只负责基础环境激活，例如 `source CANN`、`conda activate`，不堆积训练参数、实验开关和环境变量。
- 启动脚本保持简洁，复杂功能逻辑放回所属源码模块。
- 控制脚本数量，避免为每次实验、每台机器或微小参数差异复制一份。

## 5. 日志命名清晰
- 日志和运行目录尽量采用“时间戳＋用途描述”，必要时补充机器或关键配置，例如 `20261026_143000_full288_r3_check`。

## 6. 修改低侵入、易审查
- 优先选择改动范围小、职责清楚的方案，尽量保留原有接口和行为。
- 不夹带无关重构或格式化，也不为减少改动行数而到处加补丁。
